# Caravel FPGA 2026
The goal of this project is to combine the [Efabless's Caravel harness](https://caravel-harness.readthedocs.io/en/latest/) with a custom user space containing neural processing acceleration units. This repo contains the necessary tools to compile the SoC in Vivado, add the SoC to the Nexys A7 FPGA, and run a custom program on the SoC/FPGA combo.

---

# Main Branch Rule

Do not push directly to `main`.

All changes must be made on a separate branch and merged into `main` through a Pull Request.

Before merging into `main`, the Pull Request must be approved by at least one other team member. This is to prevent changes from breaking the main branch.

# Vivado Git Workflow

>[!NOTE]
>The following workflow assumes that all features have been implemented in seperate branches, such as branch_synaptic_module_integration or branch_LUT_bug_fixing, and now they must be merged together into main. Throughout this section, these modified branches are called *feature_branch*.

## Goal

Keep `main` stable. Do not directly merge large Vivado branches into `main` unless the project has already been tested.

The project *will* break when generated files, stale IP files, or project metadata are merged incorrectly. The overall steps to merge feature branches with main are below:

1. Create a fresh branch from `main`. In this example, it is called `main_integration`
2. Switch to `main_integration` and pull in only the needed source files from `feature_branch`
3. Commit and push main_integration
4. Open Vivado and generate a bitstream. If success, continue to next step, if not, fix errors then commit and push *only necessary files*.
5. Remove all "garbage" files (git reset --hard, git clean -fd)
6. Merge back into `main` after approval

More detailed steps are below:

## 1. Create a fresh branch from `main`

### 1.1 Start from `main`

```bash
git checkout main
git pull
```

This makes sure your local copy of `main` is up to date before creating a new integration branch.

### 1.2 Create the integration branch

```bash
git checkout -b main_integration
```

This branch is where you will test the feature branch changes before merging anything back into `main`.

Do not do this work directly on `main`.

## 2. Pull in only the needed source files from `feature_branch`

### 2.1 See available remote branches

```bash
git fetch --all
git branch -a
```

Remote branches appear like:

```text
remotes/origin/branch_name
```

If `feature_branch` only exists remotely, use:

```text
origin/feature_branch
```

instead of:

```text
feature_branch
```

### 2.2 Copy only important files from `feature_branch`

From `main_integration`, copy only the files that are likely to matter for Vivado:

```bash
git checkout origin/feature_branch -- "*.v" "*.sv" "*.vhd" "*.xdc" "*.tcl" "*.bd" "*.xci"
```

This is not a full merge. It only copies selected files from `feature_branch` into your current branch, `main_integration`.

*Note that you may not have `.bd` files. If your project does not use block design files, remove `"*.bd"` from the command.*

### 2.3 Do not copy generated Vivado junk

Avoid committing:

```text
.Xil/
*.runs/
*.cache/
*.sim/
*.hw/
*.jou
*.log
*.str
```

These are generated by Vivado and can break other people’s projects.

Recommended `.gitignore` additions:

```gitignore
.Xil/
*.runs/
*.cache/
*.sim/
*.hw/
*.jou
*.log
*.str
```
>[!NOTE]
>It is advisable to create a git ignore with these additions to make this workflow faster

## 3. Commit and push `main_integration`

### 3.1 Check what changed

```bash
git status
git diff --name-status
```

Only commit files that are actually needed.

Usually okay to commit:

```text
*.v
*.sv
*.vhd
*.xdc
*.tcl
*.bd
*.xci
*.xpr
```

Be careful with `.xpr`: commit it only if Vivado source registration changed, such as adding missing modules with the `+` button.

### 3.2 Commit only the necessary files

Do not blindly run `git add .` unless you have already checked that no generated Vivado files are included.

Preferred method:

```bash
git add path/to/changed/file1
git add path/to/changed/file2
git commit -m "Integrate feature branch source changes"
```
or:

```bash
git add -i
```
to use the git interactive interface.

### 3.3 Push `main_integration`

```bash
git push -u origin main_integration
```

## 4. Open Vivado and generate a bitstream

### 4.1 Open the Vivado project

After copying files and pushing `main_integration`:

1. Open the Vivado project.
2. Check that all modules are found.
3. Run synthesis.
4. Run implementation.
5. Generate a bitstream.

If the bitstream succeeds, continue to Step 5.

If the bitstream fails, fix the errors, then commit and push only the necessary files.

### 4.2 If IP is missing

If IP files are present but Vivado is not generating the needed output products:

1. Right click the `.xci`.
2. Select:

```text
Reset Output Products
Generate Output Products
```

Then rerun synthesis, implementation, and bitstream generation.

### 4.3 If Vivado says a module exists but synthesis says it is missing

Try:

```text
Sources → Compile Order → Refresh Compile Order
```

Also check for missing imported source files.

Example synthesis error:

```text
[Synth 8-439] module 'clk_fix' not found
```

This often means:

- IP output products were not generated
- compile order is stale
- required source files are missing
- imported source paths broke during merge

### 4.4 If you add missing files in Vivado

If you use the `+` icon to add missing source files, commit:

```text
The added source files
The changed .xpr file
```
>[!NOTE]
>The `.xpr` file is the main project file that stores settings, design sources, and IP configuration for the FPGA project. This updates as files are added/removed *or* as files are set as top level. 

Then:

```bash
git status
git diff --name-status
git add path/to/changed/files
git commit -m "Add missing Vivado source files"
git push
```

Do not commit generated build folders just because Vivado created them while testing.

### 4.5 If Vivado creates garbage files while testing

Vivado may create many temporary/generated files while synthesis, implementation, or bitstream generation is running.

Before committing any fixes, check:

```bash
git status
git diff --name-status
```

**Only commit files that are required for the project to open, synthesize, implement, or generate a bitstream correctly.**

## 5. Remove all garbage files

### 5.1 Reset tracked files you do not want

If Vivado changed tracked files that should not be committed, reset them:

```bash
git reset --hard
```

> Warning: this removes all uncommitted changes to tracked files.
> Only run this after you have already committed and pushed the necessary files.

### 5.2 Remove untracked generated files

To remove untracked Vivado-generated files and folders:

```bash
git clean -fd
```

> Warning: this deletes untracked files and folders.
> Use this to clean garbage files such as generated Vivado output folders.

### 5.3 Verify the branch is clean

```bash
git status
```

You should see:

```text
nothing to commit, working tree clean
```

## 6. Merge back into `main` after approval

### 6.1 Open a Pull Request

After `main_integration` has been tested successfully in Vivado and the bitstream generates, open a Pull Request from:

```text
main_integration
```

into:

```text
main
```

### 6.2 Get approval

At least one other person should review and approve the Pull Request before merging.

Nobody should approve a merge into `main` unless:

- Vivado opens correctly
- synthesis passes **on multiple machines**
- implementation passes if required
- bitstream generation succeeds
> E.g each team member should switch to the branch and generate a bitstream. **Only if successful, then proceed.**
- only necessary files are included
- no Vivado garbage files are included

### 6.3 Merge into `main`

Merge through the Pull Request after approval.

## Common Vivado Problems

### Problem: Project opens but synthesis fails

Possible causes:

- Missing source files
- Missing IP output products
- Broken compile order
- Imported paths changed during merge

### Problem: Vivado project breaks after merge

Usually caused by:

- merging generated files
- stale `.Xil`
- stale `.runs`
- imported source duplication
- broken `.xpr`

Best fix:

1. Start from clean `main`.
2. Create a fresh `main_integration` branch.
3. Copy only real source/project files from `feature_branch`.
4. Regenerate IP if needed.
5. Retest synthesis, implementation, and bitstream generation.
6. Merge only after approval.

>[!NOTE]
>Merge conflicts with `.xpr` may result from people having different files set as Top Level in Simulation. To maintain coherrency, every member (who is working on the same branch) should have the same Top Level modules set.

# [STEP 1] Vivado Project Setup & Synthesis

>[!TIP]
> We recommend the team use the **same** and **latest** version of Vivado.
 
For Vivado installations you can follow the [Vivado Installation Research Memo](./Documents/Research%20Memo%20-%20Installing%20and%20Using%20Vivado%20and%20Vitis.pdf) (it should be easily adaptable to the latest Vivado version) <br>
If you followed the Research memo for installation then you should already have the correct board files. If not, you can just look at the *Installing Board Files* section.

## Project Synthesis

Open [Our Project](./CARAVEL/) by opening the `./CARAVEL/CARAVEL.xpr` file.

Ensure the project is set to use the `xc7a100tcsg324-1` project part (part of Artix-7 family).

Set `Caravel.v` to Top Level, **not** the module called `Top Level` (it is confusing).
> Failure to follow will result in "To many I/Os utilized" error

> [!IMPORTANT]
> Ensure all Vivado IPs are updated to your version of Vivado. This can be done automatically by clicking on the un-updated IP and looking at the bottom of Vivado and click the **Update IP** button

Now you should not see any errors and should be ready to synthesize the project for the NexysA7 board.
> [!NOTE]
> If an error appears regarding "clk_fix not found" and clk_fix does exist, right click it and "Generate Output Products." This error occurs because the IP sometimes has trouble importing.

You can now generate a Bitstream file by clicking the `Generate Bitsream` in the tab on the left menu. 
**Be sure to say Yes to the Synthesize and Implement before generating Bitstream option**

Now open the Hardware Manager, connect to the board and program the FPGA.

> [!NOTE]
> If you are not familiar with using Vivado's environment you can follow our [Research Memo](./Documents/Research%20Memo%20-%20Installing%20and%20Using%20Vivado%20and%20Vitis.pdf).


# [STEP 2] Flashing code onto Caravel using PICO

You will need a Rasberry Pi Pico for the following section. 

## Setting up IDE for Pico

>[!TIP]
> If any of the steps are unclear for Thonny, it is a widely documented IDE with many resources to work with Microcontrollers and specifically Picos online

First install the [Thonny IDE](https://thonny.org/) (a python micro controller IDE).

Once the IDE is installed navigate to the `Run->Interpreter->Install or Update Micropython`. From there you can follow the instructions to install Micropython for the Pico model you are using. 

>[!NOTE]
> If your Pico is not being detected on Windows, you might not have entered the exact correct Pico model name. 

After this, simply unplugging and plugging the Pico should be sufficient for Thonny to detect it and be able to program it.

## Putting the Python scripts and C hex file onto Pico

Navigate to our `./Micropython_scripts` folder and open all the files in Thonny. To transfer files to the Pico, for each file, go to `Save As` and when asked `Where to Save to` select `Rasberry Pi Pico`. (The file names will have `[` `]` around them to indicate they are opened in Pico)

>[!NOTE]
> To open the `.hex` file in Thonny, when you navigate to the file explorer, ensure that the **all files** are selected an not just Python files to be able to see the `.hex` file.


## Connecting Pico to FPGA

Now you should be ready to connect the Pico to the FGPA, follow the pin connections below. (Disconnect the Pico from your computer before making connection and ensure the FPGA is also OFF)

Hardware connection between Pico and the Nexys FPGA board.
- FPGA PMOD `JC ground` to the Pico `ground`
- FPGA PMOD `JC1` (mprj_io[1]/SDO) will be connected to `pin 6` in Raspberry pi pico (MISO/ SPIO RX)
- FPGA PMOD `JC2` (mprj_io[2]/SDI) will be connected to `pin 5` in Raspberry pi pico (MOSI/ SPIO TX)
- FPGA PMOD `JC3` (mprj_io[3]/CSB) will be connected to `pin 7` in Raspberry pi pico (SPIO CSn)
- FPGA PMOD `JC4` (mprj_io[4]/SCK) will be connected to `pin 4` in Raspberry pi pico (SPIO SCK)


Once the connections are made, if you powered down the FPGA as instructed, you will have to re-program it with the Bitstream.

Now you can now connect the Pico to your computer and start the code flashing step. 

## Flashing Code 

Once all the above steps are done, you can flash the code onto Caravel. 

To do so, select the `main.py` file in Thonny, and then just click `Run Current Script` (The green circle button or press F5).

Now in the Thonny terminal, you will see a bunch of text relating to Flash memory etc. 
If the code flashed successfully, you should see the 7-Segment Display in Caravel starting to show hex values on loop. 

You can see the Video for correct behavior in either our project presentation or teams channel.

## 2. Explanation of changes and process flow

Code generation is done using a modified version of the [caravel_mgmt_soc_litex](https://github.com/efabless/caravel_mgmt_soc_litex) repository. 

We had to modify Makefiles and ensure the correct exports in the `~/.bashrc` (which are shown in [Process Flow section](#1-process-flow-steps)) file to get code generation working for us. <br> In this section we will present the changes we made and some rationale to why they were made.

### Makefiles

The following Makefiles were changed and why they were changed:
- [`cpu.makefile`](./caravel_mgmt_soc_litex/verilog/dv/make/cpu.makefile): Contains variable initializations for FIRMWARE source files and Caravel's verilog (including our VexRiscV core)
- [`env.makefile`](./caravel_mgmt_soc_litex/verilog/dv/make/env.makefile): Contains exports for Caravel's verilog path, core verilog path, userproject verilog path and lastly the cross compiler paths (installed above)
- [`sim.makefile`](./caravel_mgmt_soc_litex/verilog/dv/make/sim.makefile): Main Makefile to compile the hex file for the code. We had to change some makefile commands and comment out waveform simulation generation code in makefile
- [`var.makefile`](./caravel_mgmt_soc_litex/verilog/dv/make/var.makefile): Contains variable definitions used in the `sim.makefile` for compiler flags to compile the C code (eventually turned into `hex` files). The flags involve defining CPU (vexriscv for us) type, family, endianness and other cross compiler specific settings

> [!TIP]
> Currently all code is compiled in the [gpio_mgmt](./caravel_mgmt_soc_litex/verilog/dv/tests-caravel/gpio_mgmt/) folder which is the default that the code in [Caravel_on_FPGA](https://github.com/efabless/Caravel_on_FPGA) uses to compile C code to run on caravel. However, to create your own folder structure for the C project you'd have to make the appropriate changes in the `sim.makefile` and the [local Makefile](./caravel_mgmt_soc_litex/verilog/dv/tests-caravel/gpio_mgmt/Makefile) in the gpio_mgmt folder. 

### Defines and headers
All the headers that would be needed for the C code, and all external imports are present in the [Firmware](./caravel_mgmt_soc_litex/verilog/dv/firmware/) folder.

The full path to the firmware folder: `caravel_mgmt_soc_litex/verilog/dv/firmware`

This is where we discovered the wishbone enable signal (one of the things that was needed to get our C code to work)
